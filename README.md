#  伝票計算web

アルバイト先で**手書き伝票のあまりの大変さ**と、**電卓での計算時に「一度でも打ち間違えたら終わり」という頭が爆発しそうな状況**を経験したことから、個人のミスを完全に防止するために自主制作した当日決済特化型の精算管理システムです。

外部サーバーやデータベースは一切使わず、ブラウザの機能だけで動く軽量なスタンドアロン型システムです。


---

## 制作のこだわり・徹底した操作性

### 1. 現場の打鍵速度を高める「入力UX」

#### ▫️**Enterキー主体のサクサク操作**
  基本的には、Enterキーだけで次々と項目を移動して完結できるスムーズな入力フローを構築。
#### ▫️**日本語と数字が混在しても止まらないEnter遷移**
  「特別料金」や「当日支払い入場料」といった欄にかな（日本語）でカスタム名を入力し、そのまま次の数字の欄へ移動する際も、Macの日本語入力（確定操作）の仕様に極力邪魔されることなく、Enterキーの打鍵で次の枠へ進めるように調整しています。
#### ▫️**すべての数字入力エリアに搭載した「自動半角変換」**
  個数や金額の入力欄だけでなく、PayPayの入力欄や金種別枚数にいたるまで、数字を入力するすべてのエリアに自動変換機能を実装。名前に日本語を入力した流れのまま、うっかり全角の数字（例：「１０００」など）を打ち込んでしまっても、システム側が瞬時に半角数字（「1000」）へ自動変換します。計算のバグを完全に防ぎますが、よりスムーズな操作のために数字は半角での入力をおすすめする設計にしています。
#### ▫️**Enter移動とダブルクリックで確実に機能する「入力値の全選択」**
  Enterキーで枠を移動した際、または枠をダブルクリックした際は、確実に毎回100%文字が全選択（ハイライト）状態になるよう制御しています。前のデータを消す手数を完全に省き、そのまま次の数字を上書きして瞬時に入力できます。
  *（※マウスで枠を1回クリックするだけの操作だと、1回で全選択されることもあれば、うっかり2桁の数字の間にカーソルが刺さってしまい前の数字を消す手間が出るなど、操作にバラつきが起きるため、Enter移動やダブルクリックでの運用を推奨する設計にしています）*
#### ▫️**金種入力の「ループ」と全選択によるレジ締め**
  金種別枚数を入力する区分では、10,000円から1円まで順番に入力していき、最後の1円の枠でEnterキーを押すと自動的に一番上の10,000円の枠へカーソルが戻るループ仕様にしています。ここでもEnterキーによる移動時なら常に数字が確実に全選択されるため、手戻りなく何度でもスムーズに数え直しの入力が可能です。
#### ▫️**キー連打で変わる「スマートメニュー入力」**
  1伝票あたり「10枠×3項目」の入力エリアを配置。一番左の項目に数字キー（例：「5」などを打つたびに500円台、「1」などを打つたびに1000円台）と同じ価格帯ごとに頻繁に出るメニューから順番に次々と切り替わる仕様に。決定後はEnterを押して個数を入力するだけで確定します。
#### ▫️ **シンプルな入力パターンに対応**
  「左（スマートメニュー）× 右（個数）」のほか、「真ん中（直接金額入力）× 右（個数）」のどちらのパターンでも伝票をまとめられます。
#### ▫️**可視性を追求した画面・グリッド設計**
  画面全体に対する伝票のサイズ感、幅、数字入力枠一つひとつの大きさに至るまで、使いやすさを限界まで調整しています。

### 2. 「何の数字か」が一瞬でわかる視覚レイアウト

- **直感的な「右寄せ」ルール**
  画面上の「何の合計が何であるか」を誰が見ても迷わないように整理。総合計より上の区分では、すべての合計額を右寄せに統一しました。縦の桁数が綺麗に揃うため、視覚的な誤認や見間違いを徹底的に防ぎます。

### 3. メモいらずで現金・PayPayの誤差をゼロにする

#### ▫️ **現場の最大の悩み「決済混在による誤差」を解消**
  現金とPayPayの注文が入り乱れる現場でも、「総合計」から「PayPay入力額」を差し引くことで自動的に「現金売上額」を算出するロジックを採用。事前のメモ書きの手間をなくせるようにしました。
#### ▫️**昼・夜・深夜の連続イベントにも対応するPayPay控除**
  深夜イベントなどで稼働させるケースを想定し、昼までや夜までの部のPayPay売上額を個別に差し引ける入力欄も実装。複数部制のイベントでも正確な現金残高を導き出せます。
#### ▫️ **運用の流れに合わせたスマートな「金種計算（レジ締め）」フロー**
  現金売上額の算出後、そのまま「金種別枚数」を入力してレジ内の現金を検証する区分へ移行。現場のレジ締めルール（現金を数えるタイミング）に合わせて、迷わず使える仕様にしています。
  - **【売上金を抜く前】に数える場合**：
    「差額」の欄を確認します。この差額が「元のレジ金（お釣り用の準備金）の額」と一致していれば計算は合っています。
  - **【売上金を抜いた後】に数える場合**：
    「合計」の欄を確認します。この合計額が「元のレジ金（お釣り用の準備金）の額」と一致していれば計算は合っています。

### 4. イベントや運用の変化に耐える「動的な枠拡張と売上区分」

- **「売上内・売上外」を切り替える特別料金（クローク等）管理**
  毎回名前が変わる「特別料金」区分を実装。「総売上に含めるか」のチェックマークを用意し、チェックONなら総合計へ動的に名前と額を追加、OFFなら総合計の下の「売上外特別料金」として区別して表示（「クローク」といったカスタム名称も反映）できます。初期状態は1枠ですが、枠を自由に増やせ、増分もすべてリアルタイムに合計へ反映されます。
- **「当日払い前売り・当日入場料」の複数価格に対応する動的なチケット枠追加**
  本システムは「最終的な当日目の前にある現金の売上額がいくらになるかを正確に出すこと」を一番の目的としています。そのため、前売りや当日など価格が違う入場料がいくつあっても対応できるよう、枠を自由に増やせ、それぞれ分かりやすい名前に変えて当日支払い分（現金とPayPayのみ）を正しく入力・集計できるようにしました。

### 5. 誤操作を防ぎデータを守る

- **「タブを閉じても消えない」安心の自動保存**
  ブラウザのタブを誤って閉じてしまっても、同じブラウザ（同じGoogle ChromeのアカウントやSafari等）で再度URLを開けば、入力途中のデータがそのまま復元されます。画面最下部にある「完全消去ボタン」を明示的に押さない限りデータは保持され続けるため、長時間の使用でも安心して運用できます。*（※プライベートモードを除く）*
- **スタンドアロン（端末閉じ）環境でのデータ隔離**
  サーバーにデータを送信して共有する仕組みではなく、「同じ端末の同じブラウザ」の中にのみデータを保持する設計にしています。そのため、同じURLを他端末が開いても内容が共有・漏洩することは一切なく、パブリックなURLでありながら高いプライバシー性を確保しています。

## 現在の課題と改善点（リアルな現場の反省）

### ① スマートメニュー機能の形骸化
一番左の項目に数字キー（例：「5」など）を連打すると、500円台のメニューが順番に切り替わる機能を実装し、頻繁に出るメニューの順番や価格設定は唯一自分でコードにデータを打ち込んで登録しました。
しかし、実際に現場で使ってもらったところ、「数字キーを連打してメニューを探すよりも、真ん中の項目に直接『500』と金額を入力した方が早い」ということが判明し、現状あまり使われていません。
*（※開発者個人としては、値段だけが連なると数字ばかりで訳がわからなくなってしまうため、価格ごとのメニュー名選択を使う運用を推奨・推進したいと考えています）*

### ② PCとスマホにおける「利便性」の差
- **画面サイズ（一覧性）**: PCであれば1画面に伝票を最大8枚まで並べて全体の状況を一目で網羅できますが、スマホだと画面が狭く、手書きの伝票と効率があまり変わらなくなってしまいます。そのため、現状はPC環境での利用を強く推奨しています。
- **キーボード操作（サクサク感）**: PCでは物理キーボードのEnterキーでテンポよく次々と入力枠を移動できますが、スマホはOSやブラウザの仕様上、Enterキーの挙動が異なり、操作のサクサク感が損なわれてしまいます。

### ③ スマートフォン利用時の具体的な挙動の課題
伝票の一番左の項目について、PCでは数字キーとEnter入力だけで連動させられますが、スマホで開くとブラウザの仕様で必ず選択項目（プルダウン）が勝手に展開されてしまい、スムーズに次の項目へEnterで進めないという非常に大きなストレス（現象）が発生しています。これらは今後のモバイル最適化における大きな課題です。

## 技術仕様・開発環境

本システムは、外部サーバーへの依存をなくし、動作の軽量さと安全性を極限まで高めたスタンドアロン型のフロントエンド・アプリケーションです。GitHubに載せやすく、誰でも手軽に動かせるように「HTMLファイル1枚だけで完結する仕組み」にしています。

- **開発言語**: HTML / CSS / JavaScript (Vanilla JS)
- **開発ツール**: VS Code (Visual Studio Code) 
- **開発体制**: GoogleのAIにコードを書いてもらいながら共同開発を行い、システムを完成させました。
- **データ保存方法**: Web Storage API (`localStorage` によるローカル自動保存)
  - 入力した文字や数字、増やした枠の状態は、ブラウザのLocalStorageという保存領域にリアルタイムで自動保存されます。サーバーにデータを送信しないため、他人に中身を見られる心配がありません。

### 対応ブラウザについて（Google Chrome最適化）
Safariなど他のブラウザでも問題なく動作しますが、開発時にGoogle Chromeで表示・ビジュアルを確認しながら制作したため、**Google Chromeで表示した際に最も美しく、最高のパフォーマンス（見やすさ・操作性）を発揮するよう設計されています。**
他ブラウザで開いた場合でも、できればURLをコピーしてGoogle Chromeに貼り付けてのご利用を推奨しています（その方が圧倒的にビジュアル面で使いやすくなります）。

### 【ファイルを1枚にまとめた理由】
本来、Web開発ではファイルを機能ごとに分けるのが一般的ですが、一度完成したコードを後から細かく書き換える予定がないため、GitHubへのアップロードの手間を最小限に抑える目的であえて「HTMLファイル1枚」にすべてを詰め込んだ構成にしています（※手軽さを最優先にしました）。

結果として、特別な環境準備をしなくても、このファイルをブラウザ（Google Chromeなど）にドラッグ＆ドロップするだけで、その場ですぐ動かせる手軽さを実現しています。
